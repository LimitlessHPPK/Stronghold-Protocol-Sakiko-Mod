# 开发与接手（Developer Handover）

> 这份文档写给**想接手/长期开发这个 Mod 的人**。它假设你从没看过这个代码库。
> 先读 `README.md`（这版做了什么）、`docs/祥子备忘录.md`（她这一块的完整历史）、
> `docs/本地修改清单.md`（逐文件对照上游），再回来读这份。
>
> 上游原版：<https://github.com/sganggs/Stronghold-Protocol>（本项目是它的**非官方 Mod 分支**）

---

## 1. 项目是什么 / 边界在哪

- **本体**：明日方舟「卫戍协议：盟约」的**非官方同人网页复刻**（1–4 人合作自动棋），上游是 sganggs。
- **本仓库**：在上游 **v0.2.1** 之上做**本地修改**，主要成果是**新干员「丰川祥子」**（走 v0.2.x 的**自选编队**路线）
  与四项通用改进（地图缩放/平移、进战场音效修复、模组攻速词条、IPv6 双栈 + 调试端点）。
- **红线（改动前必读）**：
  1. **不提交任何官方素材**（立绘/语音/音效/字体）。仓库里没有，也**不要**提交；
     `public/assets`、`public/fonts`、`public/vendor`、`node_modules`、`.cache`、`data/local-assets.json` 全部 gitignore。
  2. **非商业**。不要加广告、付费、募捐入口，也不要搭建公开大厅对外运营。
  3. **署名与许可**：代码 GPL-3.0-or-later（`LICENSE`）；再分发必须保留 `NOTICE.md`、`THIRD-PARTY-NOTICES.md` 与上游署名。
     贡献即视为同意以同一许可发布（inbound = outbound）。
  4. **数据不是官方数据**：模式数据里没有她，她是 `tools/inject-sakiko.mjs` 注入的（幂等）；改动数据表要同步跑构建器。

## 3. 开发流程（本仓库的规矩）

```powershell
npm install                                   # 依赖（会生成 public/vendor）
node tools/fetch-assets.mjs --offline          # 素材清单（首次或改素材后）
node --test --test-concurrency=3              # 全量测试（fullmatch 系列单文件 9–11 分钟，别开高并发）
npx.cmd eslint .                              # 三道 CI 之一（本机 npx.ps1 被拦，用 npx.cmd）
npx.cmd tsc --noEmit --checkJs -p jsconfig.json
node tools/check-imports.mjs
node tools/golden.mjs                         # 黄金基线逐位比对（285 场景）
```

### 3.1 黄金基线（golden）——**最重要的纪律**

`test/golden/*.json` 记录固定种子场景的摘要，**逐位比对**。用途是让**任何改变玩法的改动显式暴露**。

- **改玩法**（加干员、改数值、改随机顺序）→ 必须 `node tools/golden.mjs --update` 并在提交信息里**逐场景解释**为什么变；
- **只想确认没改坏** → `node tools/golden.mjs`，它会打印**哪个场景的哪个字段**从旧值变成新值；
- **绝不允许**"为了让测试变绿"而无解释地重算。若变化出现在**与你改动无关的家族**（roster/bonds/fields/matches/standins）
  ⇒ 那是回归，**停下报告**。
- 生成物（`data/*.json`、`test/golden/*.json`）**一律重跑生成，不做文本合并**。

### 3.2 提交与评审

- 分支 → 改动 → 测试与 CI 全绿 → PR 到 `main`；一个 PR 只做一件事，说明里写清"改了什么/为什么/怎么验"。
- **不要**提交生成物的大规模无关重排；重建数据只提交真正变化的行。
- 触碰 `server/sim/**`（玩法）时，PR 里必须附 golden 差异解释或"零差异"的证据。

### 3.3 真浏览器验证（渲染/音频改动**必做**）

`public/js/render/**` 与 `public/js/audio.js` 的问题**可以完全逃过单测**（踩过：一个标识符写错导致整页降级为"简化视图"，
而 21 条纯函数测试全绿）。办法：

```powershell
$env:RENDER_E2E='1'; $env:CHROME_PATH='C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe'
node --test "test/render/*.browser.test.js"
node test/e2e/sakiko-note-sfx-probe.mjs --skill=0     # 真发牌 + 真部署 + 挂钩播放入口（她这一块的取证工具）
```

## 4. 已知坑（本机与上游都有）

| 坑 | 说明 |
|---|---|
| `raw.githubusercontent.com` / `github.com` 在部分网络不可达 | 用 **jsDelivr** 镜像，或 `SP_GITHUB_PROXY`（默认 gh-proxy） |
| Node 的 `fetch` 报 `UNABLE_TO_VERIFY_LEAF_SIGNATURE` | 加 **`--use-system-ca`** |
| `npx.ps1` 被执行策略拦 | 用 `npx.cmd` |
| `test/update-package.test.js` 有 1 条环境失败 | Windows 自带 bsdtar 在 GBK 控制台写中文文件名；**纯净上游同样失败**，不是回归 |
| 高并发跑测试会伪造性能基准失败 | 用 `--test-concurrency=3` |
| **v0.2.1 起上游有"增量更新包"机制** | 按 `MANIFEST.json` 校验程序文件；**本仓库文件被改过，不能用增量包升级**，只能用完整包重放（见 §5） |
| PowerShell 写中文提交信息 | 用 `git commit -F 文件`，别用多行内联字符串 |

## 5. 上游发新版了怎么办

1. **先读上游 CHANGELOG**：确认哪些是上游**已按官方重做**的（历史教训：v0.1.3→v0.1.4 的高台规则、缇缇沉睡计数），
   **不要**把本地的旧行为覆盖回去；
2. 用**完整包**做基线（不要整目录覆盖！），把本仓库的功能**逐条重放**（`git am --3way` 或手工）；
3. 生成物重跑（`build-data` / `fetch-assets` / `golden --update`），**不做文本合并**；
4. 跑测试与 golden，确认只有预期场景变化；
5. 她的数据注入脚本（`tools/inject-sakiko.mjs`）通常**不需要改**，但要确认它写的那几张表在上游仍存在。

## 6. 现在的决策规则（所有者已淡出）

所有者已明确"没有精力继续做下去、希望大家来开发"。因此：

- **常规改动**（bug 修复、性能、测试、文档、上游移植）→ **维护者自行决定**，按 §3 的流程走即可；
- **需要公开讨论的**（平衡性、是否改变她的既有语义、是否引入新的非官方干员）→ **开 Issue 讨论**，PR 里引用该 Issue；
- **仍然算"所有者裁定"的历史决定**（见 `docs/祥子备忘录.md` §4）→ **不要在没有新证据的情况下推翻**；
  要改就**在新 Issue 里给出证据**（PRTS 原文、实机录像/日志、上游变更），并在 PR 描述里写明"这是对某条历史裁定的修订"。
- **红线**（§1）**不可协商**，包括"不提交官方素材"和"非商业"。

## 7. 从哪开始？（给新人的入口）

见 **`docs/ROADMAP.md`**：按"难度 / 影响"排好的任务清单，其中标了 **good first issue** 的可以直接上手。
最省事的入门方式：

1. 跑通 `npm install` + `npm start`，玩一局（含她）；
2. 跑 `node --test "test/content/op_oblvns.test.js"`（39 项）看懂她的测试怎么写；
3. 挑一个 `docs/ROADMAP.md` 里的小任务，按 §3 的流程提 PR。
