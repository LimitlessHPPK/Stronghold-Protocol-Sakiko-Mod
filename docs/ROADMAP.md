## A. 她（丰川祥子）相关

### A1. 🟢 `noteSkill` 的诞生音/命中音按技能细分（小–中）
- **现状**：`snap.proj` 的 kind 只有 `note`（天赋音符）与 `noteSkill`（技能音符），所以技能音符的诞生音只能取一个文件
  （现在固定用 S2 钢琴的 `p_atk_mjckyrdnt_r`）；S3 法术半段（`_s3_mag`→`_p`）、S2 慢速变体（`_s2_slow_t`→`_p`）听感仍与钢琴相同。
- **在哪改**：`server/sim/battle/events.js`（kind 的写死处）+ 她的 kit（`hitTag`）给音符打更细的 tag；
  清单侧**已就绪**（`sfx.units[charId].skillSfx[i].born` 已存好对应 take）。
- **怎么验**：`test/e2e/sakiko-note-sfx-probe.mjs`（真浏览器，会打印每个音效实际播放的文件）+ 新增断言。
- **注意**：改 kind 属于**协议面**改动，要同时看客户端 `render/fx/notes.js` 与 `style.js` 的 `PROJ` 表。

### A2. S2 钢琴/风琴两种音色的区分（小）
- **现状**：两种音色的命中音在数据里同属一个 kind，目前取钢琴那份。
- **在哪改**：她的 kit 在发射风琴音符时给出可区分的 tag；清单解析侧已能分辨（`_r` / `_p` 两个 take）。
- **怎么验**：同 A1 的探针 + `test/sfx-oblvns.test.js`。

### A3. 技能期间「技能音符 + 天赋音符」两层是否合并（中，**需先讨论**）
- **现状**：S2/S3 技能期间每次攻击会同时出「技能音符 + 天赋音符」两层；官方模型下这段时间的载体**应当只有技能自己那只**。
- **历史**：所有者 2026-10-08 明确"**暂缓**"。**要动先开 Issue**，附 PRTS 依据与实机对比，再按新证据决定。
- **影响**：改这个会改她的 DPS 与 golden（含她的 `diy-135/136`）。

### A4. 攻击挥击音的 5 个"技能档"（小，**结论是不做**）
- **现状**：官方 `ON_ABILITY_ON…attack.0/1/2/3/5.1` 与 `combat.*` 全指向 `p_atk_MJCkyrdnt_h`，
  而客户端 `normalAttackSfx()` 按文件名拒绝 `_d/_h/_s` 结尾的音（防"技能命中音当普攻音播"）。
- **已核实**：当前清单里它**一条都没拒到**；若连 plan 的过滤一起去掉，会牵动 **20 名干员 / 25 处**换音（其中 17 处仍会被拒）。
- **结论**：保持现状。**除非**你要把客户端改成"**以清单为准、不再靠文件名启发式**"——那是一个独立的、值得做的重构（见 C1）。

### A5. 范围延伸（**不做**，历史裁定）
「其他 Ave Mujica 成员的攻击范围延伸」——所有者 2026-10-08 裁定**不实现**（含"另一只她自己"的情形）。
注意 PRTS 明确"另一只丰川祥子也可以符合这一条件"，所以**不要**用"没有其他成员"当理由。

## B. 引擎 / 通用能力

### B1. 🟢 把"充能至上限自动释放"做进引擎（小–中）
- **现状**：官方「可充能技能在充能次数达到上限时**立刻**产生额外效果（如立刻释放一次）」目前**只在她的 kit 里**实现
  （`chargeCapRelease`）。其它可充能干员仍依赖引擎的自动触发（要求"即将攻击 + 范围内有敌人"）。
- **为什么没做**：推广到引擎会让**其它家族**的 golden 变化（当时按"非她场景一动就是回归"的规矩停手）。
- **怎么做**：在 `server/sim/skills.js` 里实现，然后**接受并逐场景解释**其它家族的 golden 变化（这是正确做法，只是需要有人负责确认每个变化都符合预期）。
- **怎么验**：`node tools/golden.mjs` 的差异清单 + 至少一名可充能干员的实战用例。

### B2. 模组条件词条的更多形状（中）
- **现状**：`server/sim/content/traitMods.js` 只通用消费「攻击范围内存在 N 名及以上敌人时攻击速度 +X」这一形状，
  其它形状（未阻挡 / 不阻挡 / HP>50% / 地面敌人 / 复活 +30 …）仍**各自写在 kit 里**，引擎**显式拒绝**（`reason:'kit'`）以免重复加成。
- **怎么做**：一次只通用化一种形状，并且**同一次改动里删掉**对应 kit 实现（否则会 +24 这类重复加成）。
  名单见 `docs/本地修改清单.md` / `12-sakiko.md` 的相关小节。
- **风险**：动的是很多干员的数值 ⇒ golden 会有多处变化，需要逐个确认。

### B3. 自选编队的"池子外干员"能否真正上场（中，**玩法改动**）
- **现状**：调试端点可以把池子外的干员发进对局，但 `shared/diy.js checkDiyPick` 是 sim/客户端/lobby **共用**的池子闸，
  放宽它是玩法改动；现在语义是"照发 + `resolved.sim:false` + 说明"。
- **怎么做**：给 pick 加显式 force 标记并贯通 simdata/快照，客户端 UI 也要能表达"这是调试内容"。
- **注意**：不要让它变成"随便塞任何干员"的公共能力，那是平衡与版权风险。

## C. 工程质量 / 可维护性

### C1. 🟢 客户端音效判定改为"以清单为准"（小，但有价值）
- **现状**：`normalAttackSfx()` 靠**文件名后缀**（`_d/_h/_s`）判断"这是不是技能档音"，用来防止把技能命中音当普攻音播。
  这是历史补丁（当时 plan 解析错过一次）。现在清单里已经有**显式的 `attack` / `hit`** 字段，理论上可以直接信任清单。
- **怎么做**：保留一层"plan 侧的解析断言"（构建时就报错），然后在客户端删掉文件名启发式；跑全量测试 + 真浏览器抽查。
- **价值**：少一类"因为文件名而静默不响"的坑。

### C2. 🟢 把 `AGENTS.md`（内部交接笔记）搬进仓库（小）
- **现状**：开发过程中的"机器坑 / 验证命令 / 历史教训 / 所有者裁定"记在一份**仓库外**的交接文档里，
  外部贡献者看不到（部分内容已整理进 `docs/开发与接手.md`）。
- **怎么做**：把可公开的部分（不含本机路径/私人信息）整理成 `docs/开发须知.md` 或直接补充 `docs/开发与接手.md`。

### C3. 用真浏览器覆盖音效回归（中）
- **现状**：`test/e2e/sakiko-note-sfx-probe.mjs` 是**探针**（打印日志），断言能力有限；
  而"限流器在高负载下饿死事件音"这类问题**只有真浏览器能复现**（就是 §3.8 那个 bug）。
- **怎么做**：把它做成带断言的 e2e 用例（`RENDER_E2E=1` 门控），纳入 CI 的可选任务。

### C4. 上游增量更新包兼容（中，**需先讨论**）
- **现状**：v0.2.1 起上游有 `MANIFEST.json` 校验，本仓库文件被改过 ⇒ 增量包会被判定为"不是整合包"而拒绝启动。
- **可选做法**：提供一个"Mod 版增量包/补丁包"生成脚本（只打包被改过的文件 + 自己的 MANIFEST），
  让使用者能从纯净上游一键打上本 Mod。**这属于分发体验改进**，值得做。

若要做第二位，先开 Issue 讨论：**数值来源（PRTS）、技能实现的可行性、素材与语音的来源与版权**，并复用她这一套流程与测试模板。

## 附：怎么判断"我改的东西是对的"

1. **有出处**：数值/机制能指到 PRTS 或上游数据（写进注释与 `docs/research/`）；
2. **有测试**：新增行为有回归测试，并**验证过它在改动前会失败**；
3. **有证据**：观感类问题（音效、动画、范围）用**真浏览器/真对局**的日志或截图证明；
4. **golden 说得清**：变化仅限预期场景，且能逐字段解释；
5. **三道 CI 全绿**：`npx.cmd eslint .` / `tsc --noEmit --checkJs` / `node tools/check-imports.mjs`。
